# Upgrading to 1.0

What changes for a caller moving from 0.9 to 1.0, and what to do about each. Everything not
listed here keeps working unchanged. What 1.x promises from here on is in the
[compatibility policy](compatibility.md).

## Measured, not estimated

Both contract baselines were generated by the 1.0 generator from the released `v0.9.0` source
and compared with 1.0, section by section:

| Surface | 0.9 → 1.0 |
| --- | --- |
| Public C# API | One type removed: `SpreadsheetPartUtility`, below. Added: five code catalogues with 81 constants. 25 engine seams gained `[Experimental]`, below. No other line changed. |
| Plan operations, anchors, every tool's input schema | Identical. Every 0.9 request and stored plan runs unchanged. |
| Tool responses | One representative response per tool was compared, 23 responses in all. 88 property paths in 12 of them changed from PascalCase to camelCase; nothing was added, removed or retyped. Template, merge, comparison and registration responses were already camelCase. Failure, partial and cancellation states were frozen after this comparison and were not compared with 0.9. |
| Configuration keys and defaults | Identical. |
| Default value of every stable type's members | Identical. |

## What needs no migration

| You stored | In 1.0 |
| --- | --- |
| An edit plan with no `contractVersion`, or `"0.2"` | Runs unchanged, with the same change semantics and the same receipt plan hash. The committed 0.8 corpus plan is run through the direct, provider and tool paths on every build. |
| A merge plan (`version` `"1"`) | Commits as before, provided its sources still match the hashes it recorded. A plan with any other version is refused before a source is read. |
| An apply or merge receipt | Reads into `ApplyReceipt` / `DocumentMergeReceipt` unchanged. Both are still schema `1`, and a receipt that omits `receiptVersion` was written as schema `1`. |
| MCP configuration | Every key and default is unchanged. They are now recorded in the [wire contract](wire-contract.md#configuration). |

## Tool responses use camelCase property names

**Who is affected:** hosts that parse tool responses from the MCP server or the Agent Framework
tools and read PascalCase property names.

**Who is not:** anyone sending plans or requests. Input has always been read case-insensitively
and still is, so stored plans, template batches and merge requests keep working as they are.
Agents reading responses as text are unaffected in practice.

Before 1.0, a response's casing depended on how it happened to be built.
`describe_capabilities` was PascalCase throughout, `inspect_document` mixed both in one payload,
and error entries carried `Code` and `Message` beside camelCase siblings. The same concept
could change case between tools: `ParaId` from `inspect_document`, `paraId` from
`find_in_document`.

In 1.0 every property name in every tool response is camelCase.

| Response | 0.9 | 1.0 |
| --- | --- | --- |
| `describe_capabilities` | `Contracts`, `Formats[].Operations`, `Limits` | `contracts`, `formats[].operations`, `limits` |
| `inspect_document` | `paragraphs[].ParaId`, `paragraphs[].Text`, `outline[].Level` | `paragraphs[].paraId`, `paragraphs[].text`, `outline[].level` |
| Error entries | `errors[].Code`, `errors[].Message` | `errors[].code`, `errors[].message` |

Enum **values** did not change. A format is still reported as `"Word"` and a change mode as
`"Tracked"`; those are member names, not property names.

**To migrate:** read property names in camelCase. A parser that already matched names
case-insensitively needs no change.

**Watch for silent defaults.** A host that deserialises a response into the library's own types
with System.Text.Json's plain options matches names case-sensitively, and every member of those
types has a default. Nothing throws: `EngineCapabilities.Formats` comes back empty while
`Contracts.EditPlan` still reads a plausible `"0.2"`. Deserialise with the web defaults:

```csharp
var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
{
    Converters = { new JsonStringEnumConverter() }
};
var capabilities = JsonSerializer.Deserialize<EngineCapabilities>(json, options);
```

Configuration keys are a separate contract and are unchanged: `OfficeAgent:AllowCreation` and the
other settings keep the casing .NET configuration uses.

## Engine seams are experimental

**Who is affected:** code that implements or names the types format modules are built from,
such as `IFormatModule`, `IOperationHandler`, `IDocumentService` or `WordObjectMap`.

**Who is not:** hosts. `new OfficeAgentClient(new WordModule())`, `AddWordFormat()`,
`AddOfficeAgent()`, custom `IDocumentProvider` and `IConnectionAccessPolicy` implementations,
and every other documented host extension point compile exactly as before.

These 25 types are now `[Experimental("OFFICEAGENT001")]`, so naming one is error
`OFFICEAGENT001`. They are the engine's internal architecture. On netstandard2.0, adding a member
to an interface breaks every implementer, so promising them for all of 1.x would have frozen the
engine. The [compatibility policy](compatibility.md#engine-extensibility) lists them.

**To migrate:** if you build a custom format module or handler, suppress the diagnostic and
expect these types to change in minor releases:

```xml
<NoWarn>$(NoWarn);OFFICEAGENT001</NoWarn>
```

## `SpreadsheetPartUtility` is internal

It was public only so two OfficeAgent assemblies could share it. It was hidden from IntelliSense
and documented as infrastructure. Code that called it has no supported replacement; open an issue
describing the need if you relied on it.

## Cell and shape targets are named like plan anchors

**Who is affected:** hosts that read the `target` of a change or error in an Excel or PowerPoint
result, for example from `preview_plan`, `apply_plan` or `edit_document_content`.

In 0.9 a cell or shape target was reported as `{ "kind": "CellAnchor", "id": "…" }`: the C#
class name, and no sheet, cell or slide. Every other target already used its plan discriminator.
In 1.0:

```json
{ "kind": "cell", "sheetId": 1, "address": "B2" }
{ "kind": "shape", "slideId": "256", "shapeId": "4" }
```

**To migrate:** match `kind` against `cell` and `shape`, the same values a plan's `$anchor`
uses, and read the locator members instead of `id`.

## A failed save says what happened to storage

**Who is affected:** hosts that handle a failed save, create, template batch or merge.

In 0.9 a provider refusal and a write that landed but went unconfirmed both surfaced as the same
`IO` failure, and every tool error reported `committed: false`, including a cancellation after
storage had accepted the bytes. 1.0 separates the outcomes:

| 0.9 | 1.0 |
| --- | --- |
| `IO` for a taken output name (filesystem and SharePoint new versions) | `AlreadyExists` |
| `IO` when the filesystem could not publish, or SharePoint refused an upload (4xx) | `WriteRejected`: nothing was changed |
| `IO` when a registration failed after the document was written | `DocumentRegistrationFailedException`, code `RegistrationFailed`, with the stored output's name and SHA-256 |
| `IO`, a transport error, or `OperationCanceledException` after a write began | `DocumentWriteOutcomeUnknownException`, code `OutcomeUnknown`, with the output's SHA-256 |
| tool `committed: false` for all of these | tool `writeOutcome`: `notWritten`, `committed`, `writtenNotRegistered` or `unknown`, and a `possibleOutput` locator for the last two. In .NET both of those exceptions derive from `DocumentWriteRecoveryException`, which carries the same locator |
| a template batch cancelled mid-way threw, losing its committed items | it returns them, with the rest `Skipped` |

The memory connection now also refuses a new version under a name it already holds, as the other
providers did.

**To migrate:**
- Read `writeOutcome` instead of inferring from `committed: false`.
- Handle `OutcomeUnknown` by reconciling, as the [recovery guide](recovery.md) describes.
- Treat a cancellation as "nothing written" only when it arrives as `OperationCanceledException`,
  or as the tool code `cancelled`.
- A custom provider that can prove nothing was stored should throw `WriteRejected`. A plain `IO`
  is now treated as uncertain.

## Removing an unknown session document fails

**Who is affected:** callers of `remove_document`, or `MemoryDocumentProvider.RemoveAsync`, on a
memory or MCP session connection with an id the connection does not hold.

In 0.9 that call reported `removed: true`, while the filesystem and SharePoint providers refused
the same call with `not-found`, as the provider documentation said. It now fails with
`not-found` on every provider.

**To migrate:** treat `not-found` from `remove_document` as "already gone" if your workflow can
remove the same id twice.

## Stable codes are available as constants

Nothing breaks here; this is new.

Every stable failure and diagnostic code is now a public constant, beside the existing
`ValidationErrorCodes`:

| Catalogue | Covers |
| --- | --- |
| `ToolErrorCodes` | Errors a tool returns, including provider failures and `cancelled` |
| `TemplateDiagnosticCodes` | Template discovery, batch preflight and population |
| `ComparisonDiagnosticCodes` | Word comparison |
| `AssemblyDiagnosticCodes` | Word document assembly |
| `RenderFailureCodes` | `RenderResult.FailureCode` |

The string values are exactly the ones 0.9 emitted, so existing string comparisons keep working.

**To migrate, optionally:** compare against the constants instead of string literals.

```csharp
if (diagnostic.Code == TemplateDiagnosticCodes.StaleBatchPreview)
{
    // Preview the batch you intend to commit, and commit against that preview's token.
}
```

A code's value is part of the 1.0 compatibility contract. It will not change within 1.x.
